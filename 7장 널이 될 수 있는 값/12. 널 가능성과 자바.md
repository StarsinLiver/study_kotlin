### 7.12 널 가능성과 자바

코틀린은 자바 상호운용성을 자랑스럽게 강조하는 언어다. 그러나 자바 타입 시스템은 널 가능성을 지원하지 않는다. 그럼 어떻게 할 수 있을까?

첫번째로 자바 코드에도 어노테이션으로 표시된 널 가능성 정보가 있다. 이런 정보가 코드에 있으면 코틀린도 그 정보를 활용한다. 따라서 자바의 @Nullalbe String 은 코틀린 쪽에서 볼 때 String?과 같고 자바의 @NotNull String은 코틀린 쪽에서는 String 과 같다.

### 7.12.1 플랫폼 타입

플랫폼 타입은 코틀린이 널 관련 정보를 알 수 없는 타입을 말한다. 그 타입이 널이 될 수 있는 타입으로 처리해도 되고 널이 될 수 없는 타입으로 처리해도 된다. 이는 자바와 마찬가지로 플랫폼 타입에 대해 수행하는 모든 연산에 대한 책임은 우리에게 있다는 의미이다. 컴파일러는 모든 연산을 허용한다. 코틀린은 보통 널이 될 수 없는 타입의 값에 대해 널 안전성을 검사하는 연산을 수행하면 경고를 표시하지만 플랫폼 타입의 값에 대해 널 안전성 검사를 중복 수행해도 아무 경고도 표시하지 않는다. 어떤 플랫폼 타입의 값이 널이 될 수도 있음을 알리고 싶다면 그 값을 사용하기 전에 null인지 검사할 수 있다.

> 널 가능성 어노테이션이 없는 자바 클래스

```java
public class Person {
  private final String name;

  public Person(String name) {
    this.name = name;
  }
  public String getName() {
    return name;
  }
}
```

코틀린 컴파일러는 getName 함수의 경우 String 타입의 널 가능성에 대해 전혀 알 지 못한다. 따라서 널 가능성을 우리가 직접 처리해야 한다.

> kotlin null 검사 없이 자바 클래스 접근하기

```kotlin
fun yellAt(person: Person){
  println(person.name.uppercase() + "!!!")
}

fun main() {
  yellAt(Person(null))
}

// NullPointerException
```

> kotlin null 검사를 통해 자바 클래스 접근하기

```kotlin
fun yellAt(person: Person){
  println((person.name ?: "Anyone").uppercase() + "!!!")
}

fun main() {
  yellAt(Person(null))
}

// NullPointerException
```

코틀린에서는 플랫폼 타입을 선언할 수는 없다. 자바 코드에서 가져온 타입만 플랫폼 타입이 된다. 하지만 IDE나 컴파일러 오류 메시지에서는 플랫폼 타입을 볼 수도 있다.

```kotlin
val i: Int = person.name
// Error Type mismatch : inferred type is String! ...
```

String!라는 타입은 코틀린 컴파일러와 IDE에서 자바코드에서 온 플랫폼 타입을 표시하는 방법이다. 하지만 우리가 이런 타입 표기를 코틀린 코드에 사용할 수는 없고 느낌표가 이런 오류 메시지의 근원과 관련이 있는 경우가 거의 없기 때문에 보통 지나칠거싱다. ! 표기는 String! 타입의 널 가능성에 대해 아무 정보도 없다는 사실을 강조할 뿐이다.

앞에서 이야기했지만 플랫폼 타입을 널이 될 수 있는 것과 없는 타입 어느쪽으로든 사용할 수 있어 두 선언은 모두 올바른 표현이다.

```kotlin
val s: String? = person.name
val s: String = person.name
```

### 7.12.2 상속

코틀린에서 자바 메서드를 오버라이드할 때 그 메서드의 파라미터와 반환 타입을 널이 될 수 있는 타입으로 선언할지 없는 타입으로 선언할 지 결정해야 한다.

> String 파라미터가 있는 자바 인터페이스

```java
interface StringProcessor {
  void process(String value);
}
```

코틀린 컴파일러는 다음 두 표현을 다 받아들인다.

> 코틀린 자바 인터페이스를 다른 여러 널 가능성의 파라미터로 구현

```kotlin
class StringPrinter: StringProcessor {
  override fun process(value: String) ...
}

class StringPrinter: StringProcessor {
  override fun process(value: String?) ...
}
```

자바 클래스나 인터페이스를 코틀린에서 구현할 경우 널 가능성을 제대로 처리하는 일이 중요하다.
